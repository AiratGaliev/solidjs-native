# ADR-0007: Capability Security for Dynamic Modules

- Status: Accepted as target requirement; implementation deferred to M10.
- Date: 2026-11-10.

## Context

A Tauri-class application framework for SolidJS Native should eventually load UI modules at runtime, including team-authored or generated screens. Dynamic code runs inside a native host process and may otherwise inherit dangerous privileges. NSH is an implementation reference for runtime limits and capability enforcement; see the [NSH reference map](../architecture/nsh-feature-parity.md).

## Decision

- Runtime modules are packaged with manifest, version requirements, content hashes, dependencies and requested capabilities.
- Host application grants capabilities explicitly; a module cannot grant privileges to itself.
- Default policy is deny for filesystem, network, process, clipboard, external URLs, native components and other sensitive host services.
- QuickJS runtime limits cover heap, stack, execution budget and interruption.
- These limits and host capability checks are not an OS process sandbox. They do not contain a QuickJS/C engine memory-safety vulnerability or native-plugin code running in-process.
- If the product must execute genuinely hostile third-party code, isolate the runtime in a separate process with OS-enforced filesystem/network/process restrictions; otherwise restrict dynamic modules to trusted, reviewed code and explicitly granted host capabilities.
- Package signatures verify provenance/integrity but do not replace capability checks or process isolation.
- Module loading validates runtime/protocol compatibility before execution.
- Revocation and shutdown release timers, handlers, resources and native registrations.

## Consequences

- Module API must be designed around capabilities from the start.
- Package format and trust store are separate from the renderer protocol.
- AI-generated UI is not trusted merely because it is signed or generated by a first-party tool; same-process capability checks limit host API access but are not a sandbox against VM/native vulnerabilities.
- Dynamic package delivery is deferred until static app runtime and lifecycle are stable and the trust/isolation model is explicitly accepted.

## Rejected alternatives

- Give every module unrestricted native host access: rejected.
- Treat signed packages as automatically trusted: rejected.
- Build dynamic package delivery before runtime and module loader stabilize: rejected.

## Invariants

- Modules receive no ambient filesystem/process/network privileges; host API access is deny-by-default.
- Capability denial is explicit and observable.
- Heap/stack/time limits reduce resource exhaustion but do not provide process isolation or containment of native/VM exploits.
- Hostile code requires an OS-isolated process boundary or must not be loaded.
